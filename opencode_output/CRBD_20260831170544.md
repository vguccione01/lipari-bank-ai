---

## Sommario del servizio

`MovementService` implementa l'operazione `transfer` — un trasferimento cross-account
che addebita un conto sorgente e accreditare un conto destinatario, registrando due
movimenti (`TRANSFER_OUT` / `TRANSFER_IN`). Il servizio è stateless, usa constructor
injection via Lombok `@RequiredArgsConstructor`, e opera su `AccountRepository` e
`MovementRepository`.

L'operazione è annotata `@Transactional` (propagation DEFAULT = REQUIRED).
Il DTO di input (`TransferRequest`) ha validazione Jakarta (`@NotNull`, `@DecimalMin`).

## Punti di forza

| # | Aspetto | Note |
|---|---------|------|
| 1 | **BigDecimal per importi** | `TransferRequest.amount`, `Account.balance`, e `Movement.amount` sono tutti `BigDecimal`. Nessun uso di `double`/`float`. Pattern corretto per dominio monetario. |
| 2 | **Validazione input nel DTO** | `@NotNull` e `@DecimalMin("0.01")` su `TransferRequest` prevengono importi nulli o negativi. Il controller usa `@Valid`. |
| 3 | **Self-transfer check** | Linea 31: `fromAccountId.equals(toAccountId)` previene il trasferimento sullo stesso conto. |
| 4 | **Sufficient funds check** | Linea 40: `compareTo` corretto per BigDecimal (non `equals`). |
| 5 | **@RequiredArgsConstructor** | Constructor injection corretta, nessun `@Autowired` su field. |
| 6 | **CorrelationId filter** | `CorrelationIdFilter` genera/propaga UUID e lo inserisce in MDC — buona base per audit trail. |
| 7 | **BCrypt per password** | `SecurityConfig` configura `BCryptPasswordEncoder()` di default. Schema DB conferma hash BCrypt. |
| 8 | **Separazione Controller/Service** | Il controller delega correttamente la logica di business al service. |

## Findings — CRITICAL

### C-1: Race condition su saldo (double-spend)

**File:** `MovementService.java:44-47`
**Severity:** CRITICAL

**Problema:** Il saldo viene letto, modificato in memoria e salvato senza meccanismo
di concorrenza. Due transfer concorrenti dallo stesso conto possono leggere lo stesso
saldo, entrambi passare il check `compareTo`, e produrre un saldo negativo.

```java
// ANTI-PATTERN: read-modify-write senza lock
from.setBalance(from.getBalance().subtract(req.getAmount()));  // riga 44
to.setBalance(to.getBalance().add(req.getAmount()));            // riga 45
accountRepo.save(from);  // riga 46
accountRepo.save(to);    // riga 47
```

**Fix proposto:** Aggiungere `@Version` sul campo `version` di `Account` per
optimistic locking, oppure usare `SELECT ... FOR UPDATE` con una query custom:

```java
// Opzione A: Optimistic locking (consigliata)
@Entity
public class Account {
    @Version
    private Long version;
    // ...
}

// Il JPA lancia OptimisticLockException in caso di conflitto.
// Il GlobalExceptionHandler deve gestirla con HTTP 409 Conflict.

// Opzione B: Pessimistic locking
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Account a WHERE a.id = :id")
Optional<Account> findByIdForUpdate(@Param("id") Long id);
```

### C-2: Nessuna idempotenza — doppio addebito su retry

**File:** `MovementService.java:30` (annotazione + firma)
**Severity:** CRITICAL

**Problema:** Nessun `idempotency key`. Un timeout di rete sul client può causare
un retry del POST `/api/movements/transfer`, producendo un doppio addebito.
Il commento al riga 22-27 lo documenta come anti-pattern intenzionale per il bootcamp,
ma resta un gap critico per produzione.

**Fix proposto:**

```java
@Transactional
public TransferResponse transfer(TransferRequest req, String idempotencyKey) {
    // 1. Check idempotenza come prima istruzione
    Optional<Movement> existing = movementRepo
        .findByAccountIdAndIdempotencyKey(req.getFromAccountId(), idempotencyKey);
    if (existing.isPresent()) {
        return toTransferResponse(existing.get());
    }

    // 2. Logica transfer esistente...

    // 3. Salvare l'idempotencyKey nel Movement record
    out.setIdempotencyKey(idempotencyKey);
    movementRepo.save(out);

    // 4. Tabella processed_idempotency_keys con TTL 24h (opzionale, per protezione extra)
}
```

Il controller deve accettare l'header `Idempotency-Key` e passarlo al service.

### C-3: Audit trail AML incompleto — mancano correlationId, userId, ipAddress

**File:** `MovementService.java:49-65` + `Movement.java` (entity)
**Severity:** CRITICAL

**Problema:** Ogni `Movement` creato registra solo `accountId`, `type`, `amount`,
`counterpartyAccountId`, `description`, `executedAt`. Mancano i 3 campi
obbligatori per l'audit trail AML (art. 40 D.Lgs. 231/2007):

| Campo AML | Stato | Note |
|-----------|-------|------|
| `correlationId` | **MANCANTE** | Il filter lo mette in MDC ma non viene propagato al Movement |
| `userId` | **MANCANTE** | Nessuna estrazione da `SecurityContextHolder` |
| `ipAddress` | **MANCANTE** | Nessuna estrazione da `HttpServletRequest` |

**Fix proposto:**

```java
@Transactional
public TransferResponse transfer(TransferRequest req,
        String correlationId, String userId, String ipAddress) {

    // ... logica transfer ...

    Movement out = new Movement();
    out.setAccountId(from.getId());
    out.setType("TRANSFER_OUT");
    out.setAmount(req.getAmount());
    out.setCounterpartyAccountId(to.getId());
    out.setDescription(req.getDescription());
    out.setExecutedAt(Instant.now());
    // --- campi AML obbligatori ---
    out.setCorrelationId(correlationId);
    out.setUserId(userId);
    out.setIpAddress(ipAddress);
    movementRepo.save(out);

    // stessa cosa per Movement in...
}

// Nella entity Movement:
@Column(name = "correlation_id", nullable = false)
private String correlationId;

@Column(name = "user_id", nullable = false)
private String userId;

@Column(name = "ip_address", nullable = false)
private String ipAddress;
```

### C-4: Nessuno screening PEP e watchlist (OFAC/EU)

**File:** `MovementService.java:30-68`
**Severity:** CRITICAL

**Problema:** Il flow di transfer non interagisce con alcun servizio di screening
PEP (Politically Exposed Persons) o watchlist (OFAC, EU Consolidated List).
L'art. 11 D.Lgs. 231/2007 e l'art. 18 della Reg. UE 2018/843 (5a AMLD)
impongono la verifica contro le liste di sanzioni prima di eseguire operazioni
finanziarie.

**Fix proposto:**

```java
@Transactional
public TransferResponse transfer(TransferRequest req, ...) {
    // Pre-transfer screening
    pepScreeningService.checkAccount(req.getFromAccountId());
    pepScreeningService.checkAccount(req.getToAccountId());
    watchlistService.checkSanctions(req.getToAccountId());

    // ... logica transfer ...
}
```

Creare un'interfaccia `PepScreeningService` e `WatchlistService` con
implementazione stub per il bootcamp, documentata come punto di integrazione
con il sistema esterno.

### C-5: Nessun monitoraggio soglie AML (10K EUR settimanale / 5K EUR frazionamento)

**File:** `MovementService.java:30-68`
**Severity:** CRITICAL

**Problema:** Nessun hook per il controllo delle soglie operative AML:

**Fix proposto:**

```java
@Transactional
public TransferResponse transfer(TransferRequest req, ...) {

        req.getFromAccountId(), correlationId);
    thresholdService.checkStructuringPattern(
        req.getFromAccountId(), req.getToAccountId(), correlationId);

    return resp;
}
```

### C-6: Nessun meccanismo SOS/UIF

**File:** `MovementService.java` (assenza globale)
**Severity:** CRITICAL

**Problema:** Nessuna classe, servizio, o hook per la segnalazione di operazioni

### C-7: JWT secret hardcoded nel codice sorgente (contesto progetto)

**File:** `JwtService.java:23` (non MovementService, ma impatta l'intero sistema)
**Severity:** CRITICAL

**Problema:** Il secret JWT è hardcoded come costante statica:

```java
private static final String SECRET = "demo-jwt-secret-for-bootcamp-banking-system-must-be-long-enough";
```

Chiunque acceda al repo (developer, CI/CD, container dump) può firmare token
validi e impersonare qualsiasi utente.

**Fix proposto:**

```java
@Value("${jwt.secret}")
private String secret; // da env var JWT_SECRET

@PostConstruct
public void validateSecret() {
    if (secret == null || secret.length() < 32) {
        throw new IllegalStateException(
            "JWT_SECRET must be at least 32 characters (256 bit for HS256)");
    }
}
```

In `application.yml`:
```yaml
jwt:
  secret: ${JWT_SECRET}
```

### H-1: Nessun log dell'operazione di transfer

**File:** `MovementService.java` (intero file)
**Severity:** HIGH

**Problema:** Nessun logger definito nella classe, nessuna riga di log per
l'operazione più critica del sistema bancario. Per un audit trail completo
e per il debugging in produzione, ogni transfer deve generare almeno:
- Log di ingresso con parametri (senza sensibili)
- Log di successo con importi e saldo aggiornato
- Log di errore con eccezione

**Fix proposto:**

```java
@Slf4j  // Lombok
@Service
@RequiredArgsConstructor
public class MovementService {

    private final AccountRepository accountRepo;
    private final MovementRepository movementRepo;

    public TransferResponse transfer(TransferRequest req, ...) {
        log.info("Transfer initiated: from={}, to={}, amount={}, correlationId={}",
            req.getFromAccountId(), req.getToAccountId(),
            req.getAmount(), correlationId);

        try {
            // ... logica ...
            log.info("Transfer completed: outId={}, fromBalance={}, toBalance={}",
                out.getId(), from.getBalance(), to.getBalance());
            return new TransferResponse(...);
        } catch (Exception e) {
            log.error("Transfer failed: from={}, to={}, amount={}, reason={}",
                req.getFromAccountId(), req.getToAccountId(),
                req.getAmount(), e.getMessage(), e);
            throw e;
        }
    }
}
```

### H-5: Timestamp inconsistenti tra i due Movement

**File:** `MovementService.java:55, 64`
**Severity:** HIGH

**Problema:** `Instant.now()` viene chiamato due volte separatemente (righe 55 e 64).
Se il JVM è sotto pressione o il GC interviene, i due timestamp potrebbero differire,
creando un'incongruenza nel ledger (TRANSFER_OUT e TRANSFER_IN con timestamp diversi).

```java
out.setExecutedAt(Instant.now());  // riga 55
// ... separazione ...
in.setExecutedAt(Instant.now());   // riga 64
```

**Fix proposto:**

```java
Instant now = Instant.now();
out.setExecutedAt(now);
// ...
in.setExecutedAt(now);
```

### M-4: Nessuna gestione esplicita di concorrenza nel controller

**File:** `MovementController.java:19-21`
**Severity:** MEDIUM

**Problema:** Il controller non gestisce `OptimisticLockException` (o
`PessimisticLockException`) che scatteranno una volta introdotto il locking
per risolvere C-1. Il `GlobalExceptionHandler` la catturerebbe come
`RuntimeException` generica con messaggio "internal error".

**Fix proposto:** Aggiungere un handler dedicato:

```java

public ResponseEntity<Map<String, Object>> handleConflict(OptimisticLockingFailureException ex) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(errorBody(HttpStatus.CONFLICT, "Concurrent modification, please retry"));
}
```

## Giudizio complessivo

Il `MovementService` è un'implementazione funzionalmente corretta ma
**non production-ready** da una prospettiva bancaria.

**Cosa funziona bene:** La logica di business di base è solida. L'uso di
BigDecimal è corretto, la validazione DTO è presente, il self-transfer check
e il sufficient-funds check sono implementati. La dependency injection è pulita.

**Gap critici:** Il servizio manca completamente dell'infrastruttura di
compliance AML che un sistema bancario richiede per legge: audit trail con
4-tupla completa, screening PEP/watchlist, monitoraggio soglie, e
meccanismo SOS/UIF. La race condition sul saldo è un bug bancario
fondamentale che in produzione porterebbe a perdite finanziarie dirette.
L'assenza di idempotenza espone a doppio addebito su retry — un
classico incidente nei sistemi di pagamento.

**Priorità di fix raccomandata:**
1. **Sprint 1:** C-1 (race condition) + C-3 (audit trail) — impatto diretto
   su sicurezza finanziaria e compliance
2. **Sprint 2:** C-2 (idempotenza) + H-1 (logging) + H-2 (userId) +
   H-3 (status check) + H-5 (timestamp) — robustezza operativa
3. **Sprint 3:** C-4 + C-5 + C-6 (AML compliance) — conformità normativa
4. **Sprint 4:** C-7 (JWT secret) + M-* + L-* — hardening sicurezza

Il servizio come baseline di partenza per un bootcamp è accettabile.
Per un deploy in staging devono essere risolti almeno C-1 e C-3.
