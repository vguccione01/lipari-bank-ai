## Executive Summary

| Severity | Count |
|----------|-------|
| CRITICAL | 2 |
| HIGH | 2 |
| MEDIUM | 6 |
| LOW | 4 |

The application has **two critical vulnerabilities** that are directly exploitable: a **hardcoded JWT signing secret** in source code and **hardcoded database credentials** in `application.yml`. Together these allow an attacker to forge arbitrary JWT tokens (impersonating any user) and directly connect to the database. Additionally, the lack of **authorization checks** on sensitive banking endpoints (account details, transfer operations) means any authenticated user can access or manipulate any account in the system.

## Detailed Findings

### Finding 1 — CRITICAL: Hardcoded JWT Signing Secret

**File:** `src/main/java/com/lipari/bank/security/JwtService.java` : Line 23  
**CWE:** CWE-798 (Use of Hard-coded Credentials)  
**OWASP:** A07:2021 Identification & Authentication Failures

```java
private static final String SECRET = "demo-jwt-secret-for-bootcamp-banking-system-must-be-long-enough";
```

**Impact:** Any attacker with read access to the repository (including leaked images, CI artifacts, decompiled JARs, or insider threat) can:
1. Forge arbitrary JWT tokens with any `subject` claim
2. Impersonate any user (admin, root, etc.)
3. Bypass all authentication controls

This is the most severe finding. In a banking application, forged tokens mean full account takeover.

**Fix:**
```java
@Value("${jwt.secret}")
private String secret;

private SecretKey signingKey() {
    return Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
}
```

With `application.yml`:
```yaml
jwt:
  secret: ${JWT_SECRET}  # Injected from Vault / K8s Secret
```

### Finding 2 — CRITICAL: Hardcoded Database Credentials

**File:** `src/main/resources/application.yml` : Lines 6-7  
**CWE:** CWE-798 (Use of Hard-coded Credentials)  
**OWASP:** A07:2021 Identification & Authentication Failures

```yaml
spring:
  datasource:
    username: lipariuser
    password: liparipassword
```

**Impact:** Direct database access from any credential leak. In a banking context, this allows data exfiltration, manipulation of account balances, and transaction history tampering.

**Fix:** Externalize all credentials via environment variables:
```yaml
spring:

    username: ${SPRING_DATASOURCE_USERNAME}

```

### Finding 3 — HIGH: No Authorization on Banking Endpoints

**Files:**
- `SecurityConfig.java` : Lines 29-31
- `AccountController.java` : Lines 18-23
- `MovementController.java` : Lines 28-29

**CWE:** CWE-862 (Missing Authorization)  
**OWASP:** A01:2021 Broken Access Control

The security configuration only distinguishes between "authenticated" and "anonymous" — there are no `@PreAuthorize`, `@Secured`, or `@RolesAllowed` annotations anywhere in the codebase.

**Critical scenarios:**
- User `alice` (customer_id=1) can call `GET /api/accounts/2` to view Bob's account details
- User `alice` can call `GET /api/movements?accountId=2` to enumerate Bob's transactions
- User `alice` can call `POST /api/movements/transfer` to transfer money FROM Bob's account

**Fix:** Implement owner-based authorization:
```java
@GetMapping("/{id}")
@PreAuthorize("@accountSecurity.isOwner(#id, authentication.name)")
public ResponseEntity<Account> getAccount(@PathVariable Long id) { ... }
```

With a service:
```java
@Component("accountSecurity")
public class AccountSecurityService {
    public boolean isOwner(Long accountId, String username) {
        // verify account belongs to the user's customer
    }
}
```

### Finding 4 — HIGH: Actuator Fully Public

**File:** `src/main/java/com/lipari/bank/security/SecurityConfig.java` : Line 30  
**CWE:** CWE-200 (Exposure of Sensitive Information)  
**OWASP:** A05:2021 Security Misconfiguration

```java
.requestMatchers("/api/auth/**", "/actuator/**").permitAll()
```

While only `health` and `info` are currently exposed, the wildcard pattern `/actuator/**` will permit access to any future actuator endpoint added without auth. If `env`, `beans`, `configprops`, or `heapdump` are enabled, these leak secrets, environment variables, and JVM internals.

**Fix:**
```java
.requestMatchers("/api/auth/**").permitAll()
.requestMatchers("/actuator/health", "/actuator/info").permitAll()
.anyRequest().authenticated()
```

Or better — protect actuator behind a separate security filter chain with network-level restrictions.

### Finding 5 — MEDIUM: Incomplete JWT Validation

**File:** `src/main/java/com/lipari/bank/security/JwtService.java` : Lines 31-37, 40-47  
**CWE:** CWE-345 (Insufficient Verification of Data Authenticity)  
**OWASP:** A07:2021 Identification & Authentication Failures

**Token generation** — missing claims:
```java
return Jwts.builder()
        .subject(username)
        .issuedAt(new Date())
        .expiration(...)
        .signWith(signingKey())
        .compact();
```

**Missing:** `issuer`, `audience`, `id` (JTI for revocation).

**Token parsing** — no claim verification:
```java
Jwts.parser()
    .verifyWith(signingKey())
    .build()
    .parseSignedClaims(token)
```

**Missing:** `.requireIssuer("lipari.it")`, `.requireAudience("lipari-bank-api")`

Without issuer/audience validation, a token signed by the same key for a different service in the same ecosystem could be replayed here.

**Fix:**
```java
public String generate(String username) {
    return Jwts.builder()
            .subject(username)
            .issuer("lipari.it")
            .audience().add("lipari-bank-api").and()
            .id(UUID.randomUUID().toString())
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + EXPIRATION_MS))
            .signWith(signingKey())
            .compact();
}

public Claims parseToken(String token) {
    return Jwts.parser()
            .verifyWith(signingKey())
            .requireIssuer("lipari.it")
            .requireAudience("lipari-bank-api")
            .build()
            .parseSignedClaims(token)
            .getPayload();
}
```

### Finding 6 — MEDIUM: BCrypt Default Cost Factor

**File:** `src/main/java/com/lipari/bank/security/SecurityConfig.java` : Line 21  
**CWE:** CWE-916 (Use of Password Hash With Insufficient Computational Effort)  
**OWASP:** A07:2021 Identification & Authentication Failures

```java
return new BCryptPasswordEncoder();  // default cost = 10
```

BCrypt cost 10 was acceptable in 2018. For 2026, with GPU/ASIC attacks, cost factor 12-14 is recommended. NIST SP 800-63B and OWASP recommend reviewing hash cost annually.

**Fix:**
```java
return new BCryptPasswordEncoder(14);
```

Note: The seed data hashes (`$2a$10$...`) use cost 10 — these should be regenerated with the new cost factor.

### Finding 7 — MEDIUM: Missing Input Validation

**Files:**
- `AuthController.java` : Lines 21-23
- `TransferRequest.java` : Line 20

**CWE:** CWE-20 (Improper Input Validation)  
**OWASP:** A03:2021 Injection

**Login endpoint** — accepts raw `Map<String, String>` with no validation:
```java
public ResponseEntity<Map<String, String>> login(@RequestBody Map<String, String> body) {
    String username = body.get("username");
    String password = body.get("password");
```

No `@Valid`, no null checks, no length limits. A null username could cause unexpected behavior; an extremely long username could cause memory issues.

**Transfer description** — no size constraint:
```java
private String description;  // no @Size, @Max, or @NotBlank
```

An attacker could send megabytes of data in the description field, causing memory pressure or DB bloat.

**Fix:**
```java
// LoginRequest DTO
@Data
public class LoginRequest {
    @NotBlank @Size(min = 1, max = 64)
    private String username;
    @NotBlank @Size(min = 1, max = 128)
    private String password;
}

// TransferRequest - add to description
@Size(max = 255, message = "description must not exceed 255 characters")
private String description;
```

### Finding 8 — MEDIUM: Exception Messages Leak Internal Details

**Files:**
- `GlobalExceptionHandler.java` : Line 16
- `MovementService.java` : Lines 32-38, 40-42

**CWE:** CWE-209 (Generation of Error Message Containing Sensitive Information)  
**OWASP:** A04:2021 Insecure Design

```java
@ExceptionHandler(IllegalArgumentException.class)
public ResponseEntity<Map<String, Object>> handleBadRequest(IllegalArgumentException ex) {
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
        .body(errorBody(HttpStatus.BAD_REQUEST, ex.getMessage()));  // raw message to client
}
```

`MovementService` throws:
- `"source account not found"` → enables account enumeration
- `"target account not found"` → confirms account existence
- `"insufficient funds"` → reveals account balance state
- `"fromAccountId and toAccountId must differ"` → reveals business logic

**Fix:**
```java
@ExceptionHandler(IllegalArgumentException.class)
public ResponseEntity<Map<String, Object>> handleBadRequest(IllegalArgumentException ex) {
    log.warn("Bad request: {}", ex.getMessage());  // log internally
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
        .body(errorBody(HttpStatus.BAD_REQUEST, "invalid request"));
}
```

### Finding 9 — MEDIUM: Transaction Race Condition (Double-Spend)

**File:** `src/main/java/com/lipari/bank/movement/MovementService.java` : Lines 29-44  
**CWE:** CWE-362 (Concurrent Execution Using Shared Resource with Improper Synchronization)  
**OWASP:** A04:2021 Insecure Design

```java
@Transactional
public TransferResponse transfer(TransferRequest req) {
    Account from = accountRepo.findById(req.getFromAccountId())...
    if (from.getBalance().compareTo(req.getAmount()) < 0) {
        throw new IllegalArgumentException("insufficient funds");
    }
    from.setBalance(from.getBalance().subtract(req.getAmount()));
```

Two concurrent transfers on the same source account can both read the same balance, both pass the funds check, and both debit — resulting in negative balance. This is a classic TOCTOU (time-of-check/time-of-use) vulnerability.

**Fix:** Use pessimistic locking:
```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Account a WHERE a.id = :id")
Optional<Account> findByIdForUpdate(@Param("id") Long id);
```

Or add idempotency key mechanism (as noted in the code's own comment).

### Finding 10 — MEDIUM: DEBUG Logging in Production Config

**File:** `src/main/resources/application.yml` : Line 37  
**CWE:** CWE-532 (Insertion of Sensitive Information into Log File)  
**OWASP:** A09:2021 Security Logging & Monitoring Failures

```yaml
logging:
  level:
    com.lipari.bank: DEBUG
```

DEBUG logging can output request parameters, JWT tokens, SQL queries with bind parameters, and stack traces. In a banking app, this could log PII (fiscal codes, IBANs, balances) to log aggregation systems.

**Fix:** Use Spring profiles:
```yaml
# application.yml (default / production)
logging:
  level:
    com.lipari.bank: INFO

---
# application-dev.yml
spring:
  config:
    activate:
      on-profile: dev
logging:
  level:
    com.lipari.bank: DEBUG
```

### Finding 12 — LOW: No Explicit CORS Configuration

**Files:** Entire codebase — no CORS configuration found  
**CWE:** CWE-942 (Permissive Cross-domain Policy)  
**OWASP:** A05:2021 Security Misconfiguration

No `@CrossOrigin`, `CorsConfiguration`, or `WebMvcConfigurer` found. By default, Spring Security blocks cross-origin requests, which is the secure default for an API. However, the absence of explicit CORS configuration means:

1. If a frontend is added, developers will likely add `allowedOrigins("*")` as a quick fix
2. Preflight requests will fail without explicit configuration

**Fix:** Add explicit CORS configuration when frontend integration is needed:
```java
@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://lipari.it"));
    config.setAllowedMethods(List.of("GET", "POST"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    config.setAllowCredentials(true);
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}
```

### Finding 14 — LOW: Swallowed JWT Exceptions

**File:** `src/main/java/com/lipari/bank/security/JwtFilter.java` : Line 32  
**CWE:** CWE-532 (Insertion of Sensitive Information into Log File)

} catch (Exception ignored) {
    // token invalido: lasciamo proseguire, la richiesta sarà 401 sui path protetti

Silently swallowing all exceptions (including `ExpiredJwtException`, `MalformedJwtException`, `SignatureException`) prevents security monitoring. An attacker brute-forcing tokens generates no audit trail.

} catch (JwtException e) {
